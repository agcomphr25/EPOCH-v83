What I would tighten before build
1. Be careful with “all three tabs read from existing data”

That is mostly true, but the risky part is the Material Budget tab.

Production and labor can likely read pretty cleanly from existing:

production_work_orders
travelers
labor_work_sessions
labor_charge_codes

But materials depends on whether you already have:

explicit project-linked allocations
work-order-linked allocations
issued quantities by traveler/work order
cost data on the same path

So I would slightly reword that section to:

All tabs should prefer existing data sources. Production and Direct Labor must read fully from existing tables. Material Budget should use existing inventory allocation/issue/cost data where available and gracefully fall back to partial values if some project-linked material rollup paths are not yet fully normalized.

That prevents the ticket from pretending the material side is easier than it may actually be.

2. Clarify what “% production complete” means

You need one rule or the KPI will drift.

For phase 1, I would define it as:

if work orders have quantity completion fields, use
sum(quantityCompleted) / sum(quantityRequired)
otherwise fall back to
completed work orders / total work orders

That should be written into the ticket.

3. Clarify “days ahead/behind”

You need a single calculation rule.

Recommended phase-1 rule:

if dueDate is null → value is null / show em dash
if status is COMPLETE → compare completion date to due date if available
otherwise
today - dueDate
positive = behind
negative = ahead
zero = due today

Keep it simple.

4. Clarify what counts as “open blockers”

For the summary cards, define blockers as one or more of:

work order status = BLOCKED
traveler status/phase indicates blocked or hold
missing active traveler when WO is in progress
material shortage / hold if available
certification invalid on active labor session only if you want labor compliance to affect blockers

For phase 1, I would use only:

blocked work orders
blocked/open hold travelers

Then expand later.

Biggest technical risks
Risk 1: project linkage consistency

This ticket assumes:

production_work_orders.projectId is reliable
travelers link back to work orders consistently
labor sessions have projectId or can be resolved cleanly

If some labor sessions only link through traveler/work order and not directly through projectId, backend aggregation must handle both.

Risk 2: material linkage path

This is the biggest uncertainty.
You may have enough for:

allocated qty
issued qty
unit cost

But if project-level allocation is indirect, you may need to derive through:

work order
traveler
requirement/reservation
inventory transaction

That is fine for phase 1, but the implementation should be honest about any missing links.

Risk 3: certification matching

You need a clean rule for how a labor session maps to a required certification.
If not fully modeled yet, phase 1 can show:

employee certification status generally
or
certification status for department/task if resolvable
otherwise Unknown

Do not fake precision here.
