# PHASE 2 — TARGET ARCHITECTURE

Design salaried / indirect labor as synthetic sessions.

A salaried labor entry should create:

1. One punch_ledger row:
   - source = 'SALARIED_ENTRY' or 'CONVERSATIONAL_ENTRY'
   - clock_in = derived start time
   - clock_out = derived end time
   - labor_class = REGULAR / INDIRECT / OVERHEAD / G&A as applicable
   - employee_id
   - notes
   - created_by
   - audit metadata

2. One or more labor_allocations rows:
   - punch_ledger_id
   - employee_id
   - allocation_start
   - allocation_end
   - charge_code_id
   - traveler_id nullable
   - production_work_order_id nullable
   - project_id nullable
   - source = 'SALARIED_ENTRY' or 'CONVERSATIONAL_ENTRY'
   - status = CLOSED initially
   - sequence_order
   - notes
   - created_by
   - audit metadata

The system must allow salaried time to be entered as:
- direct project labor
- indirect labor
- admin
- meetings
- training
- quoting
- vendor management
- customer service
- quality review
- maintenance
- PTO reference, if already approved elsewhere

# PHASE 3 — CONVERSATIONAL TIME ENTRY DESIGN

Design the conversational time entry workflow.

The employee should be able to type natural language such as:

“Yesterday I spent 2 hours on quoting, 1.5 hours in a production meeting, and 4.5 hours on the aerospace traveler.”

or:

“Today from 8 to 10 I worked on admin, 10 to noon on vendor management, and 1 to 5 on project X.”

The system should parse this into a draft structure:

[
  {
    date,
    start_time,
    end_time,
    duration_hours,
    labor_category,
    charge_code_id,
    confidence,
    needs_review,
    explanation
  }
]

IMPORTANT:
- Conversational parsing must create DRAFT entries first
- Do NOT immediately post final labor records from AI parsing
- User must review and confirm
- Low-confidence items must be flagged
- Missing charge codes must require selection
- Ambiguous time ranges must require clarification

# PHASE 4 — DRAFT ENTRY MODEL

Before creating punch_ledger / labor_allocations, introduce a draft layer.

Design or implement a table such as:

labor_entry_drafts

Suggested fields:

- id
- employee_id
- entry_date
- raw_input_text
- parsed_segments_json
- status: DRAFT / NEEDS_REVIEW / CONFIRMED / POSTED / VOIDED
- source: MANUAL / CONVERSATIONAL / AI
- total_hours
- confidence_score
- validation_errors_json
- created_by
- reviewed_by
- reviewed_at
- posted_at
- created_at
- updated_at

Purpose:
- conversational text lands here first
- user edits draft
- user confirms
- only then does system create synthetic punch_ledger + labor_allocations

# PHASE 5 — VALIDATION RULES

Implement validation before posting:

1. No overlapping segments for same employee/date
2. Total daily hours must be visible
3. Charge code required unless mapped to approved default indirect code
4. Segment duration must be positive
5. Salaried entries cannot overlap existing approved locked entries
6. Locked / payroll-approved periods cannot be modified
7. PTO must not be manually duplicated if already approved/imported
8. All AI-derived entries must preserve the original text and parse explanation

If validation fails:
- keep draft in NEEDS_REVIEW
- do not post synthetic sessions

# PHASE 6 — POSTING LOGIC

When a draft is confirmed:

Create synthetic punch_ledger records and labor_allocations.

Preferred approach:

Option A:
- One punch_ledger row per day
- Multiple labor_allocations beneath it

Example:
8:00–5:00 salaried day
  allocation 1: 8–10 admin
  allocation 2: 10–12 quoting
  allocation 3: 1–5 project work

Option B:
- One punch_ledger row per segment

Choose the safer option based on current schema and costing logic.

My preference unless code indicates otherwise:
- one synthetic session per employee per day
- multiple allocations per session

Return your recommendation and reasoning before implementing.
