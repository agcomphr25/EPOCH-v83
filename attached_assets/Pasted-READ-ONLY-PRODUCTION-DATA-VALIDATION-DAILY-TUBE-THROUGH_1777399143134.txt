--------------------------------------------------
SECTION A — travelerBarcode LINKAGE VALIDATION
--------------------------------------------------

This is the highest-priority validation.

The board depends on this join path:

p2_layup_schedules
→ p2_serialized_items
→ travelerBarcode
→ travelers
→ traveler_steps

We must know if this works reliably in REAL production data.

Validate:

1. Of the last 60 real P2 tubes started,
how many have:

p2_serialized_items.travelerBarcode populated?

2. Of those,
how many successfully join to:

travelers.id

3. Of those,
how many successfully join to:

traveler_steps.departmentName = 'Assemble/Disassembly'

4. Return exact percentages

Example:

60 started
58 have travelerBarcode
56 join to travelers
54 join to Assemble/Disassembly step

= 90% reliable

We need exact numbers.

Not estimates.

Also identify:

- null travelerBarcode records
- malformed values
- duplicate mappings
- broken joins
- legacy inconsistencies

If reliability is below 95%,
call it out as a major implementation risk.

SECTION B — OVEN CURE LOG RELIABILITY
--------------------------------------------------

For slots 19–22:

GREEN = final required oven entry

p2_oven_cure_logs.startTime

We must validate whether this is reliable enough.

Check:

For the last 30 recently completed P2 tubes:

1. Does a p2_oven_cure_logs record exist?

2. Does startTime exist and appear timely?

3. Is startTime entered close to actual production time

4. Are there multiple logs for same serialized item?

5. Is ovenId populated consistently?

6. Is result populated reliably?

Return:

exact percentages

and

whether this is trustworthy enough for Phase 1

whether fallback to universal Assemble/Disassembly green logic is safer.
