IMPLEMENTATION PROMPT — EPOCH CHECKLIST ENGINE MIGRATION (BASED ON KENTRO PATTERN)

You are implementing a checklist architecture upgrade in EPOCH.

IMPORTANT:
- Make changes carefully and coherently.
- Preserve existing behavior where possible during transition.
- Prefer additive migration over destructive rewrite.
- Do not remove old functionality until the new path is wired and verified.
- We are using KENTRO’s checklist architecture as the conceptual model:
  template → instance → instance items → execution lifecycle

==================================================
OBJECTIVE
==================================================

EPOCH’s current checklist system is too form-based and rigid.

Current issues identified:
- legacy fallback checklist path is hardcoded in the frontend
- frequency logic is broken
- saves are batch overwrite rather than incremental/per-item
- no real instance lifecycle
- weak per-item auditability
- no role/department/group assignment model
- no manufacturing-aware triggers
- modal UX can lose data

We want to move EPOCH toward a KENTRO-style checklist engine adapted for manufacturing.

==================================================
TARGET ARCHITECTURE
==================================================

Create/extend EPOCH so checklists work like this:

1. TEMPLATE
Reusable definition of a checklist
Examples:
- Opening checklist
- Paint booth startup checklist
- Finish QC closeout checklist
- Shipping verification checklist
- Lot/batch finalization checklist

2. INSTANCE
A generated working copy of a template for a real operational context

Examples of instance context:
- employee + date
- employee + shift
- department + date
- order + stage
- lot/batch + shipping event
- machine + inspection event

3. INSTANCE ITEMS
Each template item copied into an execution row with its own state and audit fields

4. LIFECYCLE
Instance status should support at minimum:
- pending
- in_progress
- completed
- reviewed
- rejected (optional but preferred)

STEP 2 — FIX THE IMMEDIATE BUGS FIRST
==================================================

Repair the current system enough to stabilize it while migration is underway.

A. Fix frequency logic
- Repair isItemDueToday() so DAILY/WEEKLY/MONTHLY behave correctly

D. Expose save metadata

STEP 4 — CREATE INSTANCE GENERATION LOGIC
==================================================

Implement a service layer that can generate checklist instances from templates.

==================================================

Do NOT rely only on batch full-replace submit.

Add endpoints such as:

- audit event rows should be written for each meaningful change

- preserve enforcement capability for required items
