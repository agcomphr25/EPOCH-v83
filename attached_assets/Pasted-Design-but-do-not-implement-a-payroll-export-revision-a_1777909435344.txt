Design, but do not implement, a payroll export revision and adjustment model for our DCAA-oriented timekeeping system.

Context:
- Payroll export is Gusto CSV only.
- Payroll processing confirmation is manual/human-entered.
- Only OWNER/ADMIN can create exports, supersede exports, void exports, or mark payroll as processed.
- Exports are full-period only, not department-specific or partial employee exports.
- Multiple full exports for the same pay period are allowed before payroll is processed.
- Every subsequent full export for the same period should create a new revision batch.
- The previous active unprocessed export should be marked superseded.
- Exact CSV contents and checksums must be preserved for every export.
- Re-downloading a historical export must return the exact stored file/rows, not freshly recalculated data.
- Once a batch is marked processed, it becomes immutable historical evidence.
- Corrections after processing should not alter the processed batch.
- Corrections after processing should create payroll adjustments for a future payroll run, with admin choice between:
  1. include adjustment in next regular payroll export
  2. create a separate off-cycle correction export

Important policy:
- If a correction or time edit is attempted after a pay period has an active unprocessed export, the edit should be blocked until an OWNER/ADMIN explicitly supersedes or voids the active export batch with a reason.
- Do not silently mark active exports stale.
- Superseding/voiding must be auditable.
- After superseding, the correction can proceed.
- The next export for that period should be a full-period revision with revision_number incremented.
