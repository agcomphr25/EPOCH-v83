STRICT COMPLIANCE-FIRST EXECUTION

DO NOT redesign Procurement.
DO NOT build the full automatic FAR/DFARS rule engine yet.
DO NOT add AI logic.

This phase strengthens the newly implemented Procurement Compliance Review Gate by adding:

1. Permanent compliance summary visibility
2. Automatic compliance revalidation when material PO data changes

==================================================

==================================================

Make compliance status understandable, visible, and safe after review.

Current improvement already built:

- compliance review modal

- compliance badges

Now add:

==================================================
PART B — REVALIDATION / INVALIDATION ENGINE
==================================================

Problem:

A PO may be compliance-reviewed and then materially changed.

That should invalidate the review.

The system must require re-review before issue if material PO data changes after a successful review.

Material changes include:

- vendor changed
- PO line items changed
- quantity changed
- price changed materially
- PO linked order/source changed
- optional statements manually changed after review
- DPAS/compliance-related statement removed
- compliance review answers changed to blocked state
- second-party approval status changed
- vendor approval status changed

Implement a safe invalidation model.

==================================================
REQUIRED BEHAVIOR
==================================================

If PO is Reviewed and a material change occurs:

1. Set compliance review status to:

requires_attention

or equivalent existing allowed value.

2. Preserve prior review data.

3. Write audit event:

COMPLIANCE_REVIEW_INVALIDATED

Include:

- PO id
- user id
- timestamp
- reason
- changed field/action
- previous compliance status
- new compliance status

4. Show badge:

Requires Attention

5. Block PO issue until compliance review is completed again.

==================================================
IMPORTANT DESIGN REQUIREMENT
==================================================

Do NOT delete old review content.

Do NOT silently overwrite previous review evidence.

For now, if the existing schema supports only one row per PO, update status to requires_attention while preserving existing answers and notes.

If better architecture already supports history/snapshots, use it.

If not, do not overbuild history tables in this phase unless necessary.

The audit event must preserve the invalidation reason.

==================================================
BACKEND REQUIREMENTS
==================================================

Update server-side issue gate so reviewed-but-invalidated POs are blocked.

Issue allowed only if:

- compliance review exists
- review_status = reviewed
- second_party_complete = true
- vendor_approved = true

If review_status = requires_attention:

return HTTP 422 with specific reason:

“Compliance review requires attention because PO changed after review.”

Add helper/service:

invalidateVendorPoComplianceReview(poId, reason, actorId, metadata)

Use it wherever material PO changes occur.
